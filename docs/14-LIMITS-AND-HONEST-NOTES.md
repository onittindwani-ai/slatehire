# Limits and honest notes

## Not legal advice, and a person always decides
Hiring software is regulated in some places (for example notice and bias audit rules for automated tools, and anti discrimination law). Slatehire keeps a person in every decision and keeps a record, which helps, but it does not make you compliant. **Have a lawyer who knows employment and data rules where you hire review the use of this tool before the first real applicant** (notice to applicants, bias audit rules, human review, how long you keep records, the offer template). The fairness page says the same in its first line. The fairness page uses the four fifths rule as an indicator only ([facts](facts/four-fifths-rule.md)).

## Known weaknesses
- The offline scorer is word and pattern rules. It misses meaning it has no words for, and it can be fooled by a resume stuffed with the right words: a skills line or a run of repeated keywords is counted as no evidence, but a stuffed line written as a sentence can still score.
- Redaction can leave small fragments. In one seed resume a stray quote and bracket stayed after a hidden email. Names hidden by pattern can still be inferred from context a person reads.
- Resume text is the only evidence. Gaps in work history and non traditional paths can be scored lower by criteria that reward a certain shape of career. Review the criteria for that.
- Group labels are voluntary and small groups are not compared.
- The model scorer (`SCORER=model` with `LLM_BACKEND=anthropic`) is real code behind the shared wrapper: one criterion per call, the redacted resume only, every quote found again by code, the total added up by code. It has only been run against a local fake server and recorded fixtures made from that fake server. It has NEVER run with a real key, so how a real model scores real resumes, and how well it agrees with a person, is UNVERIFIED. Test it on your own fictional resumes with the held out tool (`tools/eval_independent.py`) before it scores a real applicant, and keep the lawyer review recommendation below.
- The rules scorer on two independent sets (60 resumes each, written by people who never saw the code) agreed with the key on the exact level only about 4 times in 10 and within one level about 8 times in 10 (numbers in [evaluation](EVALUATION.md)). It scores low when a resume describes the work in words the rubric does not list. A vague mention is often read as no evidence. Use a score to read, never to rank or reject.
- Redaction without a known name left name fragments in a few resumes, and street addresses or school names in forms it has no pattern for. Reference people are redacted by a pattern for a line such as Reference: Name and for a References section, not by understanding the page.
- **Scorer wording leans on some coded language.** A few rules count wording that reads as gendered or age coded, and no check yet compares the score distribution between groups beyond the fairness indicator. Read the rules in `apps/api/src/slatehire/scoring.py` with your adviser before you rely on the rules scorer for real people.
- **PDF parsing is capped, not sandboxed.** A resume file is read in the request or worker process: at most 5 MB, at most the first 12 pages, a page whose drawing instructions are over 1 MB (as stored) is skipped and said so, at most 6 seconds in all, and the text is cut at 60,000 characters. A crafted PDF can still use time and memory inside those caps, because parsing is not run in a separate process with a timeout. Run the worker with a memory limit.
- **Marking mail read** after it is dealt with is not stopped by the kill switch: the switch stops everything that leaves the app, and reading is not that. Only mail whose subject has the word "Application" is read or marked.
- **English only.** The scorer matches English words. A resume in another language would show no evidence for every criterion, so such a resume is detected by a rough count of common words and is not scored: it is flagged "Not scored: language" for a person to read (it can be shortlisted without a score). A resume that mixes languages may be sent to a person too, and a very short one cannot be told apart. Rubrics and resumes in another language need a different scorer.
- **A word or Pages file is not read.** Only PDF, text, markdown and RTF are. A Word attachment gives a flagged "Resume missing" applicant and the line says so.
- **The overview is cached.** The quote check on the page header and the Evals call are worked out again only when a score or a resume was added or removed.
- **A deleted person is kept as a hash.** To stop the same address being added again, a one way hash of it made with `SUPPRESSION_KEY` is kept (see docs/13). It is not readable, and the owner can lift it. Only the same address (after folding capitals, plus tags, full width characters and trailing punctuation) is recognised, never the same person under another address. If `SUPPRESSION_KEY` is lost the old hashes match nobody. After a restore the people who asked later are erased again from `erased-hashes-all.txt` (docs/11), which is only as complete as the last backup that saved it.
- **Hidden text is found by rules, not by looking.** Invisible, tiny, off page and white text (on a page with no dark fill) is left out of scoring and flagged. Text covered by a picture, text clipped away, and a resume that is only a picture are not found, and white text on a page with any dark fill is read as a design. The kept PDF is there so a person can look.
- **Instruction lines are judged by wording.** A line is an attack when it opens with a command or speaks to "you"; the words alone are not enough. An attacker who writes an instruction as a plain third person sentence about the candidate ("this applicant has a perfect score") can still be scored on it: the person reading sees the flag only when the wording matches. The scorer never acts on a resume, and a person decides every outcome.
- **Erasure matches words.** A name is replaced wherever it stands as a whole word, in any capitals, including the short parts of a name (Wu, Li), but never a single letter, so an initial typed on its own can stay. A phone number is found in any layout of its digits. A name written with a different spelling, or described ("the woman from Lisbon"), is not found. Deleting on request removes every application with the same normalised address; a person who applied with two addresses is two people.
- **The ATS job filter** (Greenhouse `job_id`, Workable `shortcode`, Ashby `application.list` with `jobId`) was written from the vendors' docs and is UNVERIFIED against the real services; a pull is refused for a role with no job id.
- **The web pages have no Content Security Policy.** The API sends a strict one; the Next.js pages need script and style allowances that were not tested without a browser run here, so one is not added yet.
- **Fairness subtraction.** See docs/13: with one small group, its count could be worked out from the totals shown on other pages.
- **`ALLOW_HTTP_LOCAL_TARGETS`** is one switch for every address the app fetches. The doctor reports it as a problem outside a test machine, but it is not scoped to a list of allowed addresses.
- **Postgres** specific parts (the savepoint around each mail message, the one migration) were written from how Postgres behaves and run on SQLite. Run the suite once with `TEST_POSTGRES_URL` set before you rely on them.
- Approval and audit times come from the real clock, not the demo clock, so after +1 day a request can show an earlier date than the demo date at the top.
- Redaction can leave a place word (a town name) beside the [ADDRESS] tag.

## Never run live
No adapter was run against a real Ashby, Workable, Greenhouse, Cal.com, Google, mailbox or signing service. The CI workflow builds the Docker images and starts the compose stack on a GitHub machine, but no Vercel, Railway or Hetzner account was used and the deploy files were never run on a real host. See [facts](FACTS-AND-SOURCES.md).

## Decided defaults (the implementer can change them)
Retention 365 days after a decline or withdrawal (hired people are never swept), smallest fairness group 10, the four fifths threshold, and at least 2 scorecards before an offer. These were decided for the shipped build on 2026-11-23. They are starting points, not legal advice: change them with the client's adviser, in the settings or the environment ([variables](04-ENVIRONMENT-VARIABLES.md)).
