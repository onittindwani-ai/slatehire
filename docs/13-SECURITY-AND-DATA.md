# Security and data

- **Sign in** is required on every route except sign in and the signed application webhook. Sessions are httpOnly cookies set by the web app; the API stays private. Changes through the web app need a header a cross site page cannot send.
- **Roles:** owner (everything), approver (decide approvals, send scorecards, plan and score) and an optional read only viewer. Only the owner can delete a candidate, lift an erasure block, import voluntary labels, run the fairness report, turn blind mode off for a role, run the demo reset, use the kill switch and read the audit log. Pay terms (the Offers page and the terms on an approval) are shown to the owner and the approver only: a viewer sees that an approval waits, not what it says.
- **Identity hiding** runs before anything reads a resume. While blind mode is on the server refuses to return names, emails or schools, whatever the page asks for. The same rule holds on every screen that names a person: the Candidates list, the list of applications that were not added (a person who is still hidden shows as their code, a stranger who never entered shows as the sender), the offers page and the onboarding page, and a task can be added only to someone who has been hired.
- **Untrusted text:** a resume is data. A line aimed at the reader (it opens with a command such as "ignore the rubric", or it speaks to "you", the scorer or the AI) is flagged, never scored and never quoted. A line that only has the words of an instruction (a compliance officer who "cannot bypass the approval rules", a teacher who "awarded full marks for every correct answer", an AI engineer who wrote the "system prompt") is shown as "possible instruction in the text, read by a person", and is still scored. Nothing in a resume can trigger an action. Looking for those lines is bounded (every pattern has a limit and a very long line is read in pieces), so a hostile file of 60,000 characters costs a fraction of a second. The place of each flagged line is stored with the resume when it is saved, so the overview that loads with every page does not read the resumes again.
- **Audit log:** hash chained and append only. The app refuses to edit or delete a row, and the chain check finds an edit made outside the app. The log holds the neutral candidate code, never a name or an email. A scorecard entry says only that one was sent, never what it recommends, and an approver's note stays on the approval (where deleting the candidate removes it), not in the log. Only the owner can read the log.
- **Fairness labels** sit in their own table and are read only by one module. A test checks this. Scores do not change when labels change. A group below `FAIRNESS_MIN_GROUP` is saved and shown as "fewer than N" with no counts. When a person is deleted, what they added to the counts (role, step, group label, quarter, nothing else) is kept in a running total, and the report uses the people still here plus that total, so deleting declined people does not turn their groups into "too few" (people deleted before this release were not folded and count as undisclosed). In a quarter that is over, a group with fewer than `FAIRNESS_MIN_GROUP` people is moved to "undisclosed" for that role and quarter with its counts, so the totals never hold a cell that is one person's label next to the date in the audit entry of a deletion; the quarter that is still open keeps its small cells until it ends, which is the one stretch where they can exist. An older report that flagged a group stays visible after a clean one. One limit: the pipeline page shows how many people entered each step in total, so when exactly one group is that small its count could still be worked out by subtraction from the other groups and those totals. The report is run by the owner; read it as an indicator and do not publish it with the group counts.
- **Protected traits:** a rubric that looks for a word that stands in for one (age, school, language, gender coded words; add your own in `PROXY_TERMS`) is refused when it is locked, and the source of an application is shown as a channel only while the identity is hidden.
- **Addresses people type** (a resume web address, and the web address an ATS gives for a resume file) go through a guard that refuses private networks, shared address space (100.64.0.0/10, which holds Tailscale hosts and some cloud metadata services), addresses that wrap a private IPv4 address inside an IPv6 one, odd schemes and unsafe redirects. The name is looked up once and the connection goes to the address that passed, each redirect is checked again, and a fetch has a 30 second limit.
- **Sign in:** the address is compared without spaces or capitals; tries are limited per visitor, per address and per account; an unknown address costs the same work as a wrong password. The web app passes on only the last address in `X-Forwarded-For`, because earlier ones are typed by the caller. The public demo logins and demo buttons switch off by themselves once `OWNER_PASSWORD_HASH` is set, and the API and worker refuse to start outside the demo on an example `SESSION_SECRET`.
- **Two people on every offer:** the person who asked for approval and the person who last wrote the terms both cannot approve; the approval screen shows the whole letter. A line break in a name or title cannot add a term to an offer file.
- **Rate limits behind a proxy:** sign in is limited per address, per address and account, and per account (failed tries only). A browser that signed in before carries a signed note (an httpOnly cookie, made only after a verified password) and is counted on its own, so a stranger failing at the owner's account from a shared address cannot lock it out. If the API sees a visitor address it does not trust (`FORWARDED_ALLOW_IPS` is not set, docs 06, 07 and 08) or every try comes from one address, the settings page says so.
- **API headers:** every API answer carries `Content-Security-Policy: default-src 'none'`, and the access log never carries a query string. The web pages have no Content Security Policy of their own yet (docs/14).
- **Limits:** a request is refused as it arrives when it is over `MAX_BODY_BYTES` (a resume file: `UPLOAD_MAX_BYTES`), whatever length it claims. An applicant's name and email travel in headers, so web server and proxy logs never hold them.
- **Secrets** are only in the environment, never in the repository. `python3 tools/scan_secrets.py` scans the tree.
- **Hidden text in a PDF:** text a person could not read on the page is left out of the resume that is scored and shown to the reviewer ("Hidden text found", with the words themselves only when identity is shown): drawn with no ink (text render mode 3, and an outline in white), white or within about 15 percent of the lightness of what was painted behind it, smaller than 2 points, squeezed to nothing (a horizontal scale under 10 percent), lifted or placed outside the page or the crop box or the clip, drawn fully transparent, or inside a layer that is switched off; forms are followed too. White text on a dark box that holds it is a design and is read. The invisible text layer that a scanner lays over the picture of a page is read and said so ("Text layer of a scan, read by a person"), but only on a page that is a picture and has no typed text of its own. A PDF up to `KEEP_ORIGINAL_MAX_BYTES` is kept as it arrived so a person can open it (not while identity is hidden, because the file holds the name; opening it is logged like a reveal), and it is erased with the person. Limits, in docs/14: it is a heuristic, text covered by a shape drawn later is not found, a picture never counts as a dark backdrop, and nothing is run in a separate process.
- **Which attachment is the resume:** every readable file is read (at most six), the one whose name says resume, cv or curriculum is used, then the one with the most text, and when more than one file was readable the choice is written on the resume (file names only where identity is shown).
- **Mail:** the mail server is asked for unread messages whose subject has the word "Application", so every other message in a shared inbox is never fetched, stored or marked read. A message over `IMAP_MAX_MESSAGE_BYTES` is never downloaded (only its sender is read), is listed under Not added and is marked read, and one run holds at most `IMAP_MAX_RUN_BYTES`. Messages are read with `BODY.PEEK[]` and a message is marked read only after it was dealt with and stored: added, a duplicate, or not added with a line on the Candidates page saying why (an unread message that was not added would be fetched again every five minutes and would crowd out new ones). One message that cannot be stored is skipped alone, with a reason and no candidate text in the log. Only a file that can be a resume (PDF, text, markdown, RTF) is read, in order, and the first one that gives text wins; a picture, a vCard or a calendar invite is never read as text, and a Word or Pages file is not read, so the applicant enters flagged "Resume missing". The mailbox connection checks the server certificate and name; plain text is allowed only for a server on this same computer.
- **Nobody drops out unseen:** every application that arrives by email, an ATS or a form and is not added (a duplicate, a refused file) has a line with the reason on the Candidates page. A resume nobody can read still brings the applicant in, marked "Resume missing" and not scored.
- **Personal data:** applicant text is stored. Delete on request or by retention. Deleting a person on request also deletes every other application with the same address and says exactly what was removed. Deleting takes out the resume and the kept PDF, the scores' quotes (rejected ones too), the scorecard comments, the notes and decision notes, the free text of the source, the approver's note on the offer, the intake log lines (found whatever capitals the address was typed in), and the name (the full name in any capitals and every part of two or more letters standing alone), the address and the phone number (in any layout) from the offer title, text and file (which is written again under a neutral name), the approval's summary, the calendar answer and any onboarding task. The sweep deletes declined and withdrawn people after `RETENTION_DAYS`, applicants nobody decided on after `OPEN_RETENTION_DAYS`, and old intake log lines. Backups keep it until they expire.
- **A deleted person stays deleted:** one thing is kept, a one way hash made with `SUPPRESSION_KEY`, a key that lives only in the environment (a copy of the database or of a backup cannot be used to test whether a known address was erased) of the address and of the outside reference the person arrived under (a Message-ID or an ATS id), with the date. The address is compared without capitals, spaces, a plus tag (`ann+jobs@x` is `ann@x`), full width characters or punctuation stuck to it; a different address of the same person, or Gmail dots moved, is not matched. It holds nothing readable. A mailbox that still has the message, an ATS pull or a webhook retry that brings the same address or reference again is refused and shown on the Candidates page as an "erased applicant". The owner can see how many are kept (`GET /api/suppression`) and lift one address, or one outside reference and its source, when the person applies again on purpose (`POST /api/suppression/lift`); everything kept from the same deletion goes with it, so a webhook or ATS record with the same reference is let in too. Hashes made by the first release (with a salt in the database) are still checked and lifted. The new hashes are also appended to `erased-hashes.txt`, so a restore can erase again whoever asked later (docs/11). Each line carries the time it was written, and lifting writes a line of its own (it ends in `lift`): the newest line for a hash wins, so a person who was let back in on purpose is not deleted again by a restore. The retention sweep keeps the same hash.
- **Not English:** the scorer reads English words only. A resume that does not look like English (another language or script) is not scored: it enters flagged "Not scored: language", a person reads it, and it can be shortlisted without a score. The check is a rough count of common words, not a language model: a resume that mixes languages may be sent to a person too.
- **Someone who leaves:** declining or withdrawing a person closes their waiting offer (it shows as withdrawn, the approval is rejected, and nothing can be approved or written for it afterwards).
See `SECURITY.md` for reporting a problem.
